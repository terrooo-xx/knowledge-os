## 1. 项目背景

构建一套"手机企业微信 → 本地 Codex Agent → 多项目工作区 → Knowledge OS"的远程开发与知识查询入口：

- 手机企业微信作为远程入口，随时随地发起任务；
- Codex 作为本地开发 Agent，持久会话、多轮上下文；
- 支持不同项目工作区（multi-workspace + `/workspace route`）；
- 接入 Knowledge OS MCP，能查询本地工程知识库并获得 Evidence；
- 通过 DeepSeek LLM Judge 生成正式答案，知识不足时 fail-closed 拒答；
- Windows 重启后自动恢复整套链路。

## 2. 最终架构

```text
手机企业微信
   ↓
企业微信 Bot（WebSocket）
   ↓
cc-connect v1.5.0（multi-workspace）
   ↓
Codex（持久 Session，resume）
   ↓
Workspace（/workspace route → 授权项目目录，workspace-write 沙箱）
   ↓
项目代码 / Knowledge OS MCP（knowledge_search）
   ↓
RAG（Wiki-first → RAW fallback → BGE Reranker）
   ↓
Evidence（检索证据 + 来源文件）
   ↓
DeepSeek LLM Judge（相关性判定，fail-closed）
   ↓
Answer（正式答案，deep 模式）
   ↓
企业微信（长消息拆分发完整送达）
```

各层职责：

| 层 | 职责 |
|---|---|
| 企业微信 Bot | 消息入口/出口（WebSocket 长连接） |
| cc-connect v1.5.0 | 消息路由、会话管理、multi-workspace、出站限速、启动 Codex |
| Codex | 本地 Agent（`codex exec`/`resume`），工具执行，持久 thread |
| PATH shim + launcher | 保证 cc-connect 解析到自管 codex 调用链，注入 approval/sandbox/profile 参数 |
| Workspace | `/workspace route` 绑定本地目录；workspace-write 沙箱限写工作区 |
| MCP bridge | Codex(NDJSON) ↔ Knowledge OS server(Content-Length) 传输适配 + 环境继承 |
| Knowledge OS | BGE embed/rerank、wiki_first+RAW、Evidence、Judge、Answer |
| Task Scheduler | 登录自启 cc-connect（用户级、Limited） |

## 3. P0 ~ P4-3 实施历程

### P0：企业微信远程 Codex + multi-workspace + 项目读写
- 目标：微信远程驱动 Codex，能在不同项目目录读写。
- 实施：cc-connect v1.5.0 + wecom WebSocket + Codex exec；multi-workspace + `/workspace route`；workspace-write。
- 问题/根因：初始 sandbox=read-only，无法写任何目录；binding key 写错。
- 修复：mode=auto-edit（workspace-write）；binding key 修正为 `wecom:TaoQuanYu`。
- 验证：默认目录与 Desktop\移动底盘控制器 均实测创建/读取/删除临时文件通过。
- 状态：✅

### P1：企业微信长消息稳定性
- 目标：长回复完整到达，不触发 846607。
- 根因：企业微信 Bot 限制 30条/分钟、1000条/小时；默认 display full 拆包连发。
- 修复：`[outgoing_rate_limit.platforms.wecom] max_per_second=0.4, burst=2` + `[display] mode="compact"`。
- 验证：长回复拆成多条但完整收到，未再出现 846607。
- 状态：✅

### P2：Knowledge OS MCP 接入
- 目标：微信远程 Codex 能调用 knowledge_search。
- 根因（多故障）：① `~/.codex/config.toml` 的 knowledge-os 段曾丢失；② codex 0.147.0 在 Windows 上 MCP stdio 无法解析 Content-Length 分帧；③ exec 模式下 MCP tool call 因 approval 被客户端取消。
- 修复：恢复 knowledge-os 配置；新增 NDJSON↔CL bridge；launcher 注入 `--approve-for-me` + `approval_policy=on-request` + `sandbox_mode=workspace-write`；PATH shim 保证 multi-workspace agent 也走 launcher。
- 验证：tools/call 真实到达 Knowledge OS server，返回 Evidence。
- 状态：✅

### P3：Windows 开机自启
- 目标：重启后自动恢复全部链路。
- 实施：`C:\cc-connect-mcp\start-cc-connect.ps1`（PATH 前置 shim + 幂等 + 隐藏启动 + 日志）+ 计划任务 `cc-connect-autostart`（AtLogOn、Interactive、Limited）。
- 问题：中文路径在 Windows PowerShell 5.1 下 GBK 乱码 → 包装器改为纯 ASCII + `%USERPROFILE%`。
- 验证：预重启验证 + 重启后自动启动、PATH shim 首选、wecom 订阅、workspace 恢复、单实例。
- 状态：✅

### P4：Knowledge OS Judge / Answer
- 目标：Judge 不再因 `DEEPSEEK_API_KEY` 缺失 fail-closed，answerable 查询生成正式答案。
- 实施：用户将 DEEPSEEK_API_KEY 持久化到 Windows User Environment；cc-connect 经任务重启继承。
- 验证：`STM32 DMA 怎么配置` deep → status=answerable、927 字正式答案、Judge relevant/error=false；`XYZ-9999` → knowledge_missing（fail-closed 保留）。
- 状态：✅

### P4-2：Codex App 更新导致 MCP 配置丢失
- 根因：Codex App 更新（26.715→26.814.41957）重写 `~/.codex/config.toml`，丢弃 `[mcp_servers.knowledge-os]` → `unsupported call`。
- 修复：独立 profile `~/.codex/knowledge.config.toml` + launcher 强制注入 `-p knowledge`；恢复 base config 的 knowledge-os 段。
- 验证：new thread 与 resume 均正常分发 knowledge_search；App 再重写 base config 也不影响 cc-connect 链路。
- 状态：✅

### P4-3：DEEPSEEK_API_KEY 从 Codex 到 MCP 子进程丢失
- 根因：codex 0.147.0 创建 MCP 子进程时不继承父进程任意用户环境变量（实测 bridge process env ABSENT，即使父进程 PRESENT）。
- 修复：bridge 从 Windows User 注册表（HKCU\Environment）读取缺失用户环境变量，仅内存补入 server env（不覆盖 PATH；不写文件、不打印值）。
- 验证：bridge server env KEY=PRESENT(len=35)；direct 与 cc-connect 链路 deep 查询均 answerable + 正式答案。
- 状态：✅

## 4. 关键故障与根因

### 故障 A：企业微信不能跨目录写入
- 根因：Codex 初始 `sandbox_mode=read-only`。
- 修复：multi-workspace + workspace-write + `/workspace route`。
- 最终状态：不同授权 workspace 可读写（Desktop\移动底盘控制器 实测）。

### 故障 B：企业微信消息 846607
- 根因：企业微信 Bot 发送频率限制（30/分钟、1000/小时）+ 长回复拆包连发。
- 修复：`outgoing_rate_limit`（wecom 0.4/s, burst 2）+ `display compact`。
- 最终状态：长回复完整收到，846607 未复现。

### 故障 C：workspace 未绑定
- 根因：`workspace_bindings.json` binding key 错误（曾用完整 session key / 错误组合）。
- 正确 key：`wecom:TaoQuanYu`（platform:channelID，channelID 取自 session key 第二段）。
- 最终状态：`/workspace` 与 `/workspace route` 正常，绑定持久化。

### 故障 D：MCP tools/call 被取消（user cancelled MCP tool call）
- 根因：codex exec + `approval_policy=never` 时，非交互 MCP tool call 在客户端被取消，请求未下发。
- 修复：launcher 注入 `--approve-for-me` + `approval_policy=on-request` + `sandbox_mode=workspace-write`；PATH shim 保证 cc-connect 与 multi-workspace per-workspace agent 都走 launcher。
- 最终状态：tools/call 真实到达 server。

### 故障 E：MCP unsupported call
- 根因：Codex App 更新重写 `~/.codex/config.toml`，`[mcp_servers.knowledge-os]` 消失 → 工具未注册。
- 修复：`~/.codex/knowledge.config.toml`（profile）+ launcher 强制 `-p knowledge`；并恢复 base config 段。
- 最终状态：cc-connect 不再依赖 App 基础 config 是否包含 knowledge-os。

### 故障 F：DEEPSEEK_API_KEY 未设置
- 根因：codex 0.147.0 创建 MCP 子进程不继承父进程用户环境变量；丢失点 = Codex → MCP bridge。
- 修复：bridge 从 Windows User Environment（HKCU）读取缺失变量，仅内存补入 server env。
- 注意：API Key 不写入代码、配置、日志、Vault。

- /shell：privileged 命令，未开启（admin_from 未设 → 拦截）。
- yolo：未使用。
- PATH shim：`C:\cc-connect-mcp` 前置；`where codex` 首选 `C:\cc-connect-mcp\codex.cmd`。
- MCP profile：`-p knowledge`（launcher 强制）。
- 出站限速：`[outgoing_rate_limit.platforms.wecom] max_per_second=0.4, burst=2`。
- display：`compact`。
- DEEPSEEK_API_KEY：Windows User Environment（present，len 35）；bridge 运行时从注册表读取补入 server env。**不写入任何文件**。

- ✅ admin_from disabled
- ✅ /shell disabled
- ✅ yolo disabled
- ✅ API Key 不进入文件/日志/Vault（仅 User 注册表 + 内存）
- ✅ Windows User Environment 保存 API Key
- ✅ Knowledge OS 保持 fail-closed（知识不足拒答）
- ✅ 未开放全盘写权限

**approval 行为说明（按实际版本）**：cc-connect 的 Codex exec 后端没有审批 IPC，代码硬编码 `approval_policy`；launcher 改为 `on-request` 并加 `--approve-for-me`，使 MCP tool call 等 approval 请求走自动审查放行。`on-request` **不代表**有人工审批弹窗，实际安全边界是 workspace-write 沙箱。不要将其表述为"每次操作人工确认"。
